# แนวทาง Business Model — Finca Check

**สถานะของเอกสารนี้** ไม่ใช่เอกสารเชิงบรรทัดฐาน (non-normative) เขียนขึ้นเพื่อการนำเสนอและรายงาน
เท่านั้น ไม่ activate แหล่งข้อมูล กฎ วิธีการ หรือคอมโพเนนต์ใด และไม่มีอำนาจเหนือ
[`ARCHITECTURE-FREEZE.md`](../ARCHITECTURE-FREEZE.md) หรือการตัดสินใจ LOCKED ทั้ง 41 ข้อใน
[`docs/project-overview.md`](project-overview.md) §38 ข้อเสนอใดในเอกสารนี้ที่ขัดกับการตัดสินใจ
LOCKED จะทำได้ต่อเมื่อมี ADR ที่เจ้าของโปรเจกต์อนุมัติแล้วเท่านั้น และในเอกสารนี้ได้ระบุไว้ทุกจุดว่า
ข้อใดขัดกับข้อใด

## 1. ความจริงที่ต้องพูดก่อน: MVP วันนี้ "หาเงินไม่ได้" โดยการออกแบบ

ไม่ใช่เพราะทำไม่เสร็จ แต่เพราะมีการตัดสินใจที่ล็อกไว้ปิดช่องทางรายได้ทุกทางโดยเจตนา

| LOCKED | ใจความ | ปิดรายได้แบบใด |
|---|---|---|
| #5 | ไม่มีระบบล็อกอินใน MVP | ไม่มีบัญชีผู้ใช้ จึงเก็บรายเดือนหรือผูกสัญญาไม่ได้ |
| #34 | run หมดอายุ 24 ชม. ไม่มีดาวน์โหลด ไม่มีลิงก์แชร์ ไม่มีประวัติ | ไม่มี "ชิ้นงาน" ที่ส่งมอบให้ลูกค้าถือไว้ได้ |
| #35 | `ACADEMIC_REVIEWED` ไม่ใช่การรับรองระดับวิชาชีพ | ขายเป็นเอกสารที่ใช้อ้างอิงทางวิชาชีพไม่ได้ |
| #36 | ทุกหน้าผลลัพธ์ต้องมีคำปฏิเสธความรับผิดชอบเชิงวิชาการ | ขายเป็นคำรับรองไม่ได้ |
| #4 | ไม่มี Investor Profile | ไม่มีข้อมูลผู้ใช้ไปทำ targeting หรือจับคู่ดีล |
| #41 | ภาษาไทยเท่านั้น | ตลาดจำกัดอยู่ในประเทศไทยในระยะแรก |

และยังมีข้อจำกัดเชิงเนื้อหาอีกชั้น คือส่วนประกอบทางเศรษฐศาสตร์ยังไม่ผ่านการตรวจทาน สถานะสุดท้าย
จึงเป็น "หลักฐานไม่เพียงพอ" ทุกกรณี ตาม
[`docs/adr/0001-first-increment-scope.md`](adr/0001-first-increment-scope.md)

**วิธีเล่าเรื่องนี้บนเวที** อย่าขอโทษ ให้บอกว่านี่คือการเลือก เราเลือกสร้าง "ชั้นหลักฐานที่ตรวจสอบ
ย้อนกลับได้" ให้เสร็จก่อน แล้วจึงต่อชั้นที่หาเงินได้ทับลงไป เพราะลำดับกลับกันคือสิ่งที่ทำให้บริการ
ประเมินมูลค่าด้วยอัลกอริทึมเสียความน่าเชื่อถือ — ขายตัวเลขก่อนจะตอบได้ว่าตัวเลขมาจากไหน

## 2. ใครคือคนที่ยอมจ่าย

ข้อสังเกตสำคัญ: **ผู้ที่ซื้อที่ดินเองไม่ใช่ลูกค้าที่ดี** เพราะใช้ครั้งเดียวในชีวิต ความยินดีจ่ายต่ำ
และต้นทุนการหาลูกค้าสูงกว่ามูลค่าที่ได้ ลูกค้าที่ดีคือคนที่ต้อง **ทำงานเดิมซ้ำ ๆ ทุกสัปดาห์**

| กลุ่ม | งานที่ทำซ้ำวันนี้ | สิ่งที่ระบบตัดทิ้งให้ |
|---|---|---|
| ผู้ประเมินราคาทรัพย์สิน | เปิดเว็บกรมธนารักษ์ ผังเมือง และข้อมูลประชากรทีละแห่งต่อหนึ่งงาน | เวลาค้นและจัดรูปแบบหลักฐานพร้อมการอ้างอิง |
| นายหน้าและที่ปรึกษาอสังหาฯ | ตอบลูกค้าว่าแปลงนี้สร้างอะไรได้ ด้วยข้อมูลที่ยังไม่ตรวจ | คำตอบที่มีแหล่งที่มาแนบ ลดความเสี่ยงการให้ข้อมูลผิด |
| ฝ่ายหลักประกันของสถาบันการเงิน | ตรวจว่าหลักประกันอยู่ในผังเมืองประเภทใด | การคัดกรองเบื้องต้นก่อนส่งผู้ประเมินลงพื้นที่ |
| องค์กรปกครองส่วนท้องถิ่น | ตอบคำถามประชาชนเรื่องข้อกำหนดอาคาร | กฎกระทรวงในรูปแบบที่เครื่องอ่านและอธิบายได้ |
| นักพัฒนาโครงการขนาดเล็ก | คัดแปลงหลายสิบแปลงก่อนลงทุนศึกษาจริง | การคัดออกก่อนจ้างที่ปรึกษา |

ทั้งห้ากลุ่มมีลักษณะร่วมกันคือ **ต้องแสดงให้คนอื่นเห็นว่าข้อสรุปมาจากไหน** ซึ่งตรงกับสิ่งเดียวที่
ระบบนี้ทำได้ดีกว่าคู่แข่ง

## 3. คุณค่าที่ขายได้จริง

ขายผิด: "ระบบบอกว่าที่ดินคุณควรทำอะไร" — เป็นคำที่ทั้งเกินความสามารถของระบบและเกินกว่าหลักฐาน
จะรองรับ

ขายถูก: **"ลดเวลารวบรวมหลักฐานจากหลายชั่วโมงเหลือหลายนาที โดยทุกตัวเลขยังชี้กลับไปยังแหล่งที่มา
ปีข้อมูล และข้อจำกัดของมันได้"**

สิ่งที่ทำให้ข้อนี้ขายได้คือมันเป็นงานที่ลูกค้าทำอยู่แล้ว เสียเวลาอยู่แล้ว และตรวจสอบผลได้ทันทีว่าจริง
หรือไม่จริง ต่างจากการทำนายมูลค่า ซึ่งลูกค้าพิสูจน์ถูกผิดไม่ได้จนกว่าจะสายเกินไป

## 4. ช่องทางรายได้ เรียงตามความเป็นไปได้

| # | รูปแบบ | ใครจ่าย | ต้องปลดล็อกอะไรก่อน |
|---|---|---|---|
| 1 | **ขายสิทธิ์ใช้ชุดกฎที่เครื่องอ่านได้** (rule pack licensing) ให้ผู้พัฒนาซอฟต์แวร์อสังหาฯ หรือสถาบันการเงินนำไปฝังในระบบตัวเอง | B2B | ไม่ขัด LOCKED ข้อใด เพราะขายชุดกฎ ไม่ใช่ผลวิเคราะห์ |
| 2 | **โครงการตามสัญญากับหน่วยงานรัฐหรือ อปท.** เพื่อแปลงข้อกำหนดท้องถิ่นเป็นชุดกฎที่ตรวจได้ | B2G | ไม่ขัด LOCKED แต่ต้องมีกำลังคนตรวจทานเพิ่ม |
| 3 | **บัญชีสำหรับมืออาชีพ** รายเดือนต่อที่นั่ง พร้อมประวัติงานและรายงานที่บันทึกได้ | ผู้ประเมิน สำนักงานนายหน้า | ขัด LOCKED #5 (ล็อกอิน) และ #34 (ประวัติ/ส่งออก) — **ต้องมี ADR และเวอร์ชันสถาปัตยกรรมใหม่** |
| 4 | **คิดค่าบริการต่อรายงาน** | รายครั้ง | ขัด #34 เช่นกัน และต้องทบทวน #35/#36 ว่ารายงานที่ขายได้ต้องมีสถานะการตรวจทานระดับใด |
| 5 | **API สำหรับคัดกรองจำนวนมาก** | นักพัฒนาโครงการ กองทุน | ต้องมีการยืนยันตัวตนผู้เรียกและเพดานการใช้ จึงขัด #5 |
| 6 | เวอร์ชันภาษาอังกฤษสำหรับนักลงทุนต่างชาติ | B2B | ขัด #41 |

**ที่ไม่ควรทำเด็ดขาด** โฆษณาจากผู้ขายที่ดิน และค่านายหน้าจากดีลที่เกิดขึ้น ทั้งสองอย่างสร้าง
ผลประโยชน์ทับซ้อนกับสิ่งที่เป็นแกนของสินค้า คือความเป็นกลางของหลักฐาน เมื่อผู้ใช้สงสัยว่าผลลัพธ์
เอนไปทางผู้จ่ายเงิน คุณค่าทั้งหมดหายไปในครั้งเดียว

**ลำดับที่แนะนำ** เริ่มจาก 1 และ 2 ก่อน เพราะทำได้ภายใต้สถาปัตยกรรมที่ freeze ไว้แล้ว ไม่ต้องรอ
ADR และเป็นการขายสิ่งที่เรามีจริง คือชุดกฎที่ตรวจทานแล้วและโครงสร้างหลักฐาน ไม่ใช่สิ่งที่เรายังไม่มี
คือบทสรุปทางการเงิน

## 5. โครงสร้างต้นทุน

**ต้นทุนส่วนเพิ่มต่อการวิเคราะห์หนึ่งครั้งต่ำมากโดยการออกแบบ**

- production ตั้งเป็น `RECORDED_AI` จึงไม่เรียกโมเดลภาษาเลย ค่า AI ต่อ run เท่ากับศูนย์
- แม้เปิด `LIVE_AI` ก็ถูกจำกัดที่ `AI_MAX_CALLS_PER_RUN=2` ตายตัว ค่า AI จึงมีเพดานบนที่คำนวณได้
  ล่วงหน้า ไม่ใช่ตัวเลขที่โตตามการใช้งานแบบไร้ขอบเขต
- การดึงข้อมูลจากแหล่งภายนอกถูกย้ายออกจากเส้นทางที่ผู้ใช้รออยู่แล้ว run จึงอ่านจากข้อมูลที่เตรียมไว้
- ที่เหลือคือ Worker CPU และคำสั่ง query ซึ่งเป็นหน่วยที่ถูกที่สุดในกองต้นทุนทั้งหมด

**ต้นทุนจริงอยู่ที่คน ไม่ใช่เครื่อง** รายการที่แพงคือการตรวจทานชุดกฎให้คงสถานะ `ACADEMIC_REVIEWED`
และการปรับข้อมูลให้ทันปีประกาศใหม่ ทั้งสองอย่างเป็นต้นทุนคงที่ ไม่โตตามจำนวนผู้ใช้ ซึ่งให้ผลสองด้าน

- ด้านดี เมื่อมีผู้ใช้มากขึ้น ต้นทุนต่อผู้ใช้ลดลงเร็ว
- ด้านเสี่ยง คอขวดของการเติบโตไม่ใช่เงินหรือเซิร์ฟเวอร์ แต่คือ **กำลังคนที่มีคุณสมบัติตรวจทานชุดกฎ**
  ข้อนี้ควรพูดบนเวทีด้วย เพราะกรรมการจะถามว่าขยายได้จริงหรือไม่

**ตัวเลขต้นทุนต่อ run ยังไม่ได้วัด** และเอกสารนี้จะไม่อ้างตัวเลขที่ยังไม่วัด เครื่องมือวัดมีอยู่แล้วคือ
ตาราง `operations.ai_call_log` (จำนวน token และเวลาต่อการเรียกแต่ละครั้ง) และคำสั่ง `pnpm benchmark`
ควรวัดก่อนนำเสนอหากต้องตอบคำถามเรื่องกำไรขั้นต้น

## 6. ตั้งราคาอย่างไร

ไม่ควรตั้งราคาจากต้นทุน เพราะต้นทุนส่วนเพิ่มเกือบเป็นศูนย์ ให้ตั้งจาก **เวลาที่ลูกค้าประหยัดได้**

วิธีหาตัวเลขที่ปกป้องได้บนเวที

1. จับเวลาจริงว่าผู้ประเมินหนึ่งคนใช้เวลาเท่าใดในการรวบรวมหลักฐานชุดเดียวกันด้วยมือ
2. จับเวลาเดียวกันบนระบบ
3. คูณส่วนต่างด้วยค่าแรงต่อชั่วโมงของวิชาชีพนั้น ได้มูลค่าที่สร้างต่อหนึ่งงาน
4. ตั้งราคาที่สัดส่วนหนึ่งของมูลค่านั้น

ขั้นที่ 1 และ 2 ทำได้ภายในหนึ่งวันด้วยอาสาสมัครสามถึงห้าคน และให้ตัวเลขที่หนักแน่นกว่าการอ้าง
ขนาดตลาดระดับหมื่นล้าน ซึ่งกรรมการได้ยินมาแล้วจากทุกทีม

## 7. ทำไมต้องเป็นเรา

คำถามที่กรรมการจะถามคือ "ถ้าดีจริง ทำไมรายใหญ่ไม่ทำ" คำตอบที่มีน้ำหนักมีสี่ข้อ

1. **ชุดกฎที่แปลงเป็นเครื่องอ่านได้และมีผู้ตรวจทานลงชื่อ** กฎกระทรวง ฉบับที่ 55 จำนวน 15 ข้อ
   ไม่ใช่งานที่ลอกได้ด้วยการเขียนโค้ด ต้องมีคนอ่านกฎหมายแล้วตัดสินว่าแต่ละข้อใช้ค่าจากอะไร
2. **โครงสร้างการสืบย้อนที่ฝังอยู่ในสคีมา** ไม่ใช่ฟีเจอร์ที่เติมภายหลัง คู่แข่งที่เริ่มจากการโชว์ตัวเลข
   ต้องรื้อฐานข้อมูลใหม่เพื่อให้ได้คุณสมบัตินี้
3. **ความซื่อสัตย์ต่อสถานะ "ยังตรวจไม่ได้"** เป็นข้อเดียวที่ทำให้ระบบนี้ใช้ในงานที่ต้องตรวจสอบ
   ย้อนกลับได้ ขณะที่ระบบซึ่งเดาค่าเพื่อให้ผลลัพธ์ดูสมบูรณ์ใช้ไม่ได้
4. **ความครอบคลุม 77 จังหวัดตั้งแต่วันแรก** ไม่ได้เริ่มจากกรุงเทพฯ แล้วค่อยขยาย

ข้อ 3 เป็นข้อที่แปลกที่สุดและควรเน้นที่สุด เพราะเป็นข้อที่คู่แข่งเชิงพาณิชย์ **ไม่อยากลอก** ไม่ใช่
ลอกไม่ได้ การยอมบอกว่า "ไม่รู้" ขัดกับแรงจูงใจทางการตลาดของพวกเขาโดยตรง

## 8. ความเสี่ยงที่ต้องยอมรับบนเวที

| ความเสี่ยง | ทำอะไรได้ |
|---|---|
| กฎหมายวิชาชีพประเมินมูลค่าทรัพย์สิน ระบบไม่ใช่และต้องไม่อ้างเป็นผู้ประเมิน | คงคำปฏิเสธความรับผิดชอบไว้ และวางตำแหน่งเป็นเครื่องมือก่อนจ้างผู้ประเมิน ไม่ใช่แทน |
| ข้อมูลล้าสมัยเมื่อมีประกาศรอบใหม่ | ระบบแสดงปีข้อมูลทุกรายการอยู่แล้ว ต้องเพิ่มกระบวนการเฝ้าประกาศ |
| สิทธิ์การใช้ข้อมูลเปลี่ยน | บันทึกเงื่อนไขสิทธิ์รายแหล่งไว้ใน `docs/data-sources/` แล้ว และเคยปฏิเสธแหล่งที่เงื่อนไขไม่เอื้อ (กรมบังคับคดี) |
| หน่วยงานรัฐทำเองและให้ฟรี | เป็นผลลัพธ์ที่ดีต่อสาธารณะ และยังเหลือช่องทางที่ 1 คือการแปลงให้เครื่องอ่านได้ |
| พึ่งผู้ให้บริการ AI รายเดียว | ชุดกฎและการตรวจสอบเป็นแบบกำหนดผลตายตัว ไม่พึ่ง AI อยู่แล้ว AI ทำหน้าที่เสนอแนวคิดเท่านั้น |

## 9. เส้นทางจากวันนี้ไปถึงรายได้

| ระยะ | ทำอะไร | ต้องมี ADR |
|---|---|---|
| วันนี้ | ส่งงานวิชาการ คงสถานะ inactive ของทุกอย่างที่ยังไม่ผ่าน gate | ไม่ |
| ถัดไป | วัดเวลาที่ประหยัดได้กับผู้ใช้จริง 3–5 คน และวัดต้นทุนต่อ run | ไม่ |
| ถัดไป | เปิดส่วนประกอบทางเศรษฐศาสตร์ผ่าน gate ใน [`docs/implementation-plan.md`](implementation-plan.md) §4 เพื่อให้สถานะสุดท้ายเป็นอย่างอื่นได้ | ไม่ แต่ต้องผ่าน gate |
| ถัดไป | ช่องทางที่ 1 และ 2 ขายชุดกฎและงานตามสัญญา | ไม่ |
| หลังจากนั้น | ช่องทางที่ 3 ถึง 5 บัญชีผู้ใช้ รายงานที่บันทึกได้ และ API | **ใช่** ขัด LOCKED #5 และ #34 |

ลำดับนี้มีเหตุผลที่สำคัญ คือทุกขั้นก่อนขั้นสุดท้ายทำได้โดยไม่ต้องแก้สถาปัตยกรรมที่ freeze ไว้เลย

## 10. สามบรรทัดสำหรับพูดบนเวที

1. เราไม่ขายการทำนายราคา เราขายการรวบรวมหลักฐานที่ตรวจสอบย้อนกลับได้ ซึ่งเป็นงานที่ผู้ประเมิน
   นายหน้า และฝ่ายหลักประกันเสียเวลาทำด้วยมืออยู่ทุกวัน
2. ต้นทุนต่อการวิเคราะห์หนึ่งครั้งเกือบเป็นศูนย์ ต้นทุนจริงคือการตรวจทานชุดกฎ ซึ่งเป็นต้นทุนคงที่
   คอขวดของเราจึงเป็นกำลังคนตรวจทาน ไม่ใช่เซิร์ฟเวอร์
3. ช่องทางรายได้สองช่องทางแรกทำได้ภายใต้สถาปัตยกรรมที่ล็อกไว้แล้ว ส่วนช่องทางที่ต้องมีบัญชีผู้ใช้
   ขัดกับการตัดสินใจที่ล็อกไว้สองข้อ และเราจะไม่แก้มันโดยไม่มีเอกสารการตัดสินใจ
